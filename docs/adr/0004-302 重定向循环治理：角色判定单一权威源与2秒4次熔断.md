# ADR-0004: 302 重定向循环治理：角色判定单一权威源与2秒4次熔断

## 状态

已接受（2026-11-20）

## 背景

全站 302 共 27 处，存在 3 条入环路径，全部汇聚于 `/user/login` ↔ `/user/verify` 二元环：

- `user.py:117`（login GET：按 **DB 角色**（经 30s 缓存）判 admin 且未验证 → 302 `/user/verify`）；
- `user.py:210`（verify GET：按 **`session["role"]`**（登录时快照，永不失效）判 admin → 302 `/user/login`）；
- 成环条件：普通用户登录后被外部 `UPDATE users SET role='admin'` 提升 → 两端判定源不一致，互相 302；
- 三个入环入口：任意受保护页（`admin_service.py:497` → `auth_utils.py:54`）、`/admin/*`（`user_utils.py:490`）、`/user/login` 本身。

全站无任何服务端重定向计数（grep 0 命中）；浏览器侧约 20 跳后 `ERR_TOO_MANY_REDIRECTS`，而 ipguard 会把循环中的用户按 `(ip,path)` 滑窗从 429 升级为封 IP、乃至**永久封禁+禁号**（`rate_limiter.py:21,109-132`，`ip_bans` 持久化重启不解除）——是伤害性副作用而非保护。

附带缺陷：`app.py:167` 用 `startswith("/setup")` 豁免，会误豁免 `/setupfoo` 类挂载路径（`auth_utils.py:24` 已是精确写法）。

## 决策

1. **角色判定单一权威源**：verify 页角色判定由 `session["role"]` 改为 `get_user(session["username"])`（DB 经 `load_users` 30s 缓存），与 login、`auth_utils`、`require_superadmin` 同源；`session["role"]` 仅保留写入（`user.py:152`）作兼容遗留，不再被任何判定读取（全库 grep 读点仅 `user.py:210` 一处）。
2. **服务端 302 硬熔断（兜底）**：`security.py` 新增 `init_redirect_circuit_breaker(app)`，在 `after_request` 对 302 响应于 session 记录时间戳滑窗；**2 秒窗口内累计第 4 次 302 → 返回 508 Loop Detected**（用户指定），移除 `Location`，写结构化 warning 日志；非 302 响应清零窗口。
3. **setup 豁免收紧**：`app.py:167` 改为 `path == "/setup" or path.startswith("/setup/")`。

放弃的备选：

- **仅熔断不统一判定源**：环仍在，用户看到的是 508 而非登录成功，"外部改 role 后会话行为错乱"未解决；
- **仅统一判定源不加熔断**：未来新增中间件仍可能造环，当前无任何兜底；
- **依赖 ipguard 滑窗当刹车**：伤害性（永久封禁持久化，重启不解除）。

## 后果

- 正：三条入环路径全部断开；任意未知环 2 秒内熔断为 508 并留结构化日志；外部改 role 在缓存 TTL 内全链路一致；
- 负：`/user/login`、`/user/verify` 每请求多一次用户缓存查询（微秒级）；`session["role"]` 成为不参与判定的遗留字段；
- 契约变化（对外可观察，故立此 ADR）：`/user/verify` 对"DB 角色为 admin 且未验证"的会话由 302 改为渲染 200（修环本体）；新增 508 状态码。测试将锚定：login→verify 一跳可达、verify 对非 admin 一跳回 login、2s 内第 4 个 302 变 508、窗口过期复位。
