# ADR-0007: UID分区模型与超管启动迁移强化

- 状态：已接受
- 日期：2026-11-20

## 背景

现状「超级管理员」以「`id ∈ 0-9` 且 `role='admin'`」为核心判定，`is_superadmin` 列为启动迁移维护的派生标记，但模型不完整、有漏洞：

1. **uid 分配无序**：`register_user` 用 `MAX(id)+1` 自动分配，不约束落段，普通用户可能拿到 ≤99 的小 id，未来与 0-9 超管区语义混淆；前端注册表单无法手动指定 uid。
2. **越界超管不清退**：启动迁移 `_migrate_superadmin` 只「提权 0-9」，不纠正「id>9 且 `is_superadmin=1`」的账号。带外手工改库给 id>9 账号打超管标记（或把 session 角色与 DB 角色造成双源冲突）不会被启动校正——这正是历史上 login↔主页 302 死循环场景的源头。
3. **兜底与规则潜在打架**：`ensure_admin_exists`（ADR-0003）「始终保留一个可用 admin」，但其「创建用 `MAX(id)+1`」「提权取最老用户」都可能落到 id>9；一旦新模型启用「越界超管清退」，这种 id>9 的兜底 admin 会被清退，兜底失效。
4. **待遇/保护 key 在 `role=='admin'`**：登录 16 位动态验证码、反馈提交不限次、「不可禁用/删除管理员」都以 `role=='admin'` 为 key，导致普通管理员（本应等同普通用户）也享有管理员待遇，且超管无法管理普通管理员。

目标：建立「超管唯一区间 + 越界清退 + 落段校验 + 手动指定 + 自动分配起点 + 兜底对齐 + 待遇/保护收窄」的完整不变量，并对未来新增身份开放。当前库仅 `admin`(id=2) 落在 0-9，无存量迁移冲突。

## 决策

**UID 分区（负向定义，对新身份开放）：**

| uid | 允许身份 | 启动期 | 手动 | 自动 |
|---|---|---|---|---|
| 0-9 | 仅超管（`role='admin'`+`id∈0-9`）| 一律 `role='admin'`/`is_superadmin=1`/`enabled=1` | ❌ | ❌ |
| 10 | 系统保留 | — | ❌ | ❌ |
| 11-99 | 所有非超管身份；`role='admin'` 只能落此段 | 不转换 | ✅ | ❌ |
| 100-1000 | 所有 `role≠'admin'` 身份 | 不转换 | ✅(限非admin) | ❌ 保留不取 |
| 1001+ | 所有 `role≠'admin'` 身份 | 不转换 | ✅(限非admin) | ✅ 起点 |

两条硬规则：**R1** `id∈0-9` 即超管（维持 `role='admin'` 组合判定，不新增 role 值，`is_superadmin` 为启动期同步的派生标记）；**R2** `id>9` 且 `is_superadmin=1` 启动时 `enabled=0`/`is_superadmin=0` 清退。落段约束：`role='admin'` ⇒ `uid∈[11,99]`；其余身份 ⇒ `uid∈[11,∞)` 且 `≠10`。

**启动迁移 `_migrate_superadmin()`** 强化为幂等权威校正：①补 `is_superadmin` 列（兼容旧库）；②0-9 一律 `role='admin'`/`is_superadmin=1`/`enabled=1`（提权+强制启用）；③`id>9 且 is_superadmin=1` 清退禁用。

**`ensure_admin_exists()` 对齐**：兜底产生的 admin 永远落在 0-9 最小空位——admin 行不可用且 id>9 时重定位其行到 0-9 空位；提权最老用户时若其 id>9 迁到 0-9 空位；表空创建时 id 取 0-9 最小空位。绝不让兜底 admin 落到 id>9（避免被 R2 清退）。

**`register_user(username, password, role="user", uid=None)`**：`role∈{user,api,admin}`。自动分配（`uid=None`）：admin 从 11 起、其余从 1001 起取首个空位。手动指定（`uid` 非空）：0-9/10 拒绝（保留区）；admin 仅 11-99 合法；非 admin 在 `[11,∞)` 合法（含 11-99/100-1000/1001+）；占用拒绝；落库 `is_superadmin=0`。前端注册表单新增可选 UID 输入框（后端为权威，前端仅体验预检）。角色下拉维持 3 项，不加超管项。

**待遇收窄**：登录/已登录/verify 入口的「16 位动态验证码」、`auth_utils` 管理员验证分支、「反馈提交不限次」由 `role=='admin'` 收窄为 `is_superadmin(user)`。普通管理员（11-99）自此免验证、反馈受 3 次限制，等同普通用户。

**保护收窄**：`admin_service` 的「不能禁用/删除管理员」由 `role=='admin'` 收窄为「仅保护 `is_superadmin`（0-9）」。超管可禁用/删除普通管理员（11-99）与普通用户；不可动其他 0-9 超管；不可操作自己（保留）。

**放弃的备选**：①新增独立 `role='superadmin'` 值——需同步改 8 处 `role=='admin'` 判断、迁移存量、扩前端下拉，改动面大且破坏「超管沿用管理员既有行为」的兼容性，弃；维持 `role='admin'`+id 区间组合。②`uid=10` 并入普通区/超管区——采用「并入系统保留区」，缝隙归保留语义最干净。③`ensure_admin_exists` 不动、接受 R2 冲突——会破坏「始终有可用超管」兜底，弃。

## 后果

**正面**：超管判定单一权威（id 区间），越界提权被启动自动清退，根治带外改库造成的双源角色冲突；uid 语义显式分区、可手动指定、对新身份开放；普通管理员回归普通用户待遇（符合「还没想好它能做什么」的意图），超管可管理普通管理员；兜底与清退规则自洽不互斥。

**负面/代价**：`ensure_admin_exists` 引入「id 重定位」（改 users 主键 id）——需确认无其它表以 users.id 作外键（当前 schema 未见，`active_sessions`/`favorites` 以 username 为主键，不受影响）；保留段 100-1000 手动可建 user/api 但自动分配永不落此段，两段语义仅靠 UI 文案区分，需在 placeholder 说明。

**对契约/goldens**：不改测试 golden（用户管理相关 golden 不在本轮变更面）；新增 `tests/test_uid_partition.py` 锚定启动迁移、兜底对齐、注册校验矩阵、待遇/保护收窄；存量 467 测试须保持全绿。

**范围外**：反馈上传安全加固（非白名单拒绝 + magic-bytes + serve 显式 mimetype）为单独一轮；画廊重写为独立任务。
