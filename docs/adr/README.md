# ADR（架构决策记录）索引与使用说明

ADR（Architecture Decision Record）记录"为什么这样做"的决策档案。本项目采用四节模板：**状态 / 背景 / 决策 / 后果**，缺一不可。

## 何时必须写 ADR

> **凡改对外可观察行为，先写 ADR 再动手。**

判定标准（满足任一条即"对外可观察行为变更"，必须先有 ADR）：

1. **API 响应结构或语义变化**：字段增删、状态码变化、错误信息文案变化、默认值变化。
2. **页面可见行为变化**：交互流程、展示逻辑、默认视图。
3. **权限边界变化**：谁能访问/修改什么。
4. **数据格式或存储语义变化**：文件结构、状态机、持久化行为的用户可观察差异。
5. **改动测试 golden（契约期望样例）**：goldens 是契约的机器可读表达，改 golden 必须先有 ADR 说明为什么契约要变，否则收工门禁直接打回。

**不算行为变更、无需 ADR**（写进说明以免误伤）：
- 纯新增独立工具/模块，不改变任何既有对外行为（例：D1 新增 `session.py` 会话工具，属新增能力而非行为变更，不需要 ADR）。
- 纯内部重构，行为契约由既有 specs + goldens 契约测试锚定且不发生任何变化（如 C5 的 file_utils 迁移与加锁——行为由契约测试证明不变）。
- 修 bug 使实现回归既有契约（契约本身没变，实现错了）。

## 模板

```markdown
# ADR-NNNN：<标题>

- 状态：proposed / accepted / superseded by ADR-XXXX
- 日期：YYYY-MM-DD

## 背景
<为什么需要决策：问题、约束、相关 bug/需求>

## 决策
<决定做什么、关键取值、放弃的备选方案及理由>

## 后果
<正面影响、负面影响与代价、对既有契约/goldens 的影响>
```
